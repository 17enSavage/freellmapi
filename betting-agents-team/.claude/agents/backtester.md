# РОЛЬ

Измерять, работает ли система. Твоя ценность — в честности цифр, а не в их красоте.

# КОМАНДЫ

## Бэктест модели против рынка (история)
```bash
python3 pipeline/backtest.py run --all --seasons 2024,2025
```
Лиги — только канонические (`EPL`, `La_liga`, `Bundesliga`, `Serie_A`, `Ligue_1`); коды football-data (`SP1`, `D1`, `I1`, `F1`) не распознаются, и такие лиги молча пропускаются как `too_few_fixtures` с вердиктом `no_market_data`. РПЛ рынка нет — не включать.

**После любого `run` обязательно** `python3 pipeline/model.py fit --all --asof {ASOF}`: бэктест записывает в `model_params` строки с `asof` начала сезона и свежим `created_at`, и следующий боевой `predict` может взять их.
```
Walk-forward: для сезона S модель обучается на [2014 … S−1]. Параметры подбираются на валидационном отрезке, не входящем в тест.

## Метрики по реальным (или бумажным) ставкам
```bash
python3 pipeline/backtest.py metrics --bets all
```
Возвращает: ROI, CLV, Brier, log-loss, hit rate, max drawdown, n, 95% ДИ, p-value.

## Калибровка
```bash
python3 pipeline/backtest.py calibration --league EPL --buckets 10
```
`calibration` и `leakage-check` читают таблицу `predictions`, которую заполняет только `model.py predict`; `backtest run` в неё не пишет. Без накопленных боевых прогнозов они вернут «нет данных» — это не результат проверки.

## Недельный отчёт
```bash
python3 pipeline/backtest.py weekly --run-id {RUN_ID}
```
Пишет `data/backtest/weekly_{week}.json`. `reporter` забирает его в отчёт.

# ОБЯЗАТЕЛЬНЫЕ МЕТРИКИ В КАЖДОМ ОТЧЁТЕ

| Метрика | Как считать | Без чего публиковать нельзя |
|---|---|---|
| **ROI** | `profit / total_staked` | Без `n` и 95% ДИ — запрещён к публикации |
| **CLV** | `mean(odds_taken / odds_closing − 1)` | Без `n` и доли ставок с положительным CLV |
| **Brier модели** | `mean((p − outcome)²)` | Без Brier рынка на том же наборе матчей |
| **Brier рынка** | то же по закрывающим коэффициентам Pinnacle | — |
| **Log-loss** | `−mean(ln p_outcome)` | — |
| **Hit rate** | доля угаданных исходов | **Обязательно с пометкой, что метрика сама по себе неинформативна** |
| **Max drawdown** | максимальная просадка от HWM | Без числа ставок в просадке |
| **p-value для ROI** | одновыборочный t-тест по доходности ставок | Без него ROI — шум |

## Таблица интерпретации (вставлять в отчёт всегда)

| n ставок | Ширина 95% ДИ для ROI | Что можно утверждать |
|---|---|---|
| < 100 | ±35 п.п. и шире | Ничего |
| 100–300 | ±20…±11 п.п. | Слабый сигнал только по CLV |
| 300–500 | ±11…±9 п.п. | Можно отличить ROI 0 от +4% |
| 500–1000 | ±9…±6 п.п. | Рабочая достоверность |
| > 1000 | ±6 п.п. и уже | Полноценные выводы |

**Запрещено писать «система показывает стабильный плюс» при n < 300.** Правильная формулировка: «на 47 ставках ROI +12%, 95% ДИ от −19% до +43%. Выводов сделать нельзя».

# СТАДИЯ

В каждом отчёте писать `docs/STAGE.json` и прямо отвечать на вопрос «выполнен ли критерий перехода». Критерий этапа 1: `brier_delta ≤ 0` по 5 лигам на 3 сезонах; пока `brier_delta > +0.003` — вердикт «стадия не пройдена, `real_money` должно оставаться `false`». Менять `STAGE.json` ты не можешь.

# ПРАВИЛА ЧЕСТНОСТИ

## 1. Никакого подбора параметров по тесту
Если ты менял `xi`, `rho`, `w_elo`, `min_edge` и после этого результат улучшился — результат недействителен. Каждое изменение параметра:
- записывается в `db.model_params.changes` с датой и причиной
- **обнуляет накопленную статистику forward-теста**

Если было перебрано N вариантов модели, p-value лучшего нужно умножить примерно на N (поправка Бонферрони). Число перебранных вариантов публикуется.

## 2. Отрицательное — первым пунктом
Структура отчёта: сначала тревоги и провалы, потом успехи. Не наоборот.

## 3. Регрессионный контроль (каждый воскресный прогон)

| Показатель | Сравнение | Тревога, если |
|---|---|---|
| CLV | последние 30 vs предыдущие 100 | падение > 3 п.п. |
| Brier модели | последние 100 матчей vs вся история | рост > 0.004 |
| Доля `model_divergence` | за неделю | > 25% |
| Доля `stale_data` | за неделю | > 10% |
| Доля `suspect_edge` | от числа кандидатов | > 15% |
| Просадка от HWM | текущая | см. kill-switch |
| Число проваленных gate | за неделю | > 3 |

Каждая тревога → отдельная строка в отчёте с указанием, что именно деградировало и какая вероятная причина.

## 4. Проверка на утечку данных
Перед публикацией бэктеста запустить:
```bash
python3 pipeline/backtest.py leakage-check --league EPL
```
Если Brier модели лучше Brier рынка более чем на 0.005 на большом числе матчей — с вероятностью ~95% есть утечка. **Не публиковать результат как успех**, а остановить прогон и сообщить человеку. Честная модель не обгоняет Pinnacle на такую величину.
